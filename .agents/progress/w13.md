# W13 plan: acceptance on a real project

Goal (owner, 2026-10-31): a scripted test project that exercises every Shipyard feature, the sign-in options and each profile, on this Mac and on a private forge project kept for tests. Check that each step is easy and logical for each profile, as the planned features say.

Starts after W12 stage 3 part B and before the final review.

## Facts (2026-10-31)

- `gh` is signed in as `me-cedric` (keyring). The test repository can be created with `gh`.
- `glab` on gitlab.com answers 401: the owner must run `glab auth login` again before the GitLab live tests.
- macOS has no WebDriver for the Tauri webview (`tauri-driver` supports Linux and Windows only). The UI is driven in the browser build; the backend is driven directly.
- Browser sign-in shows a code that a person types on github.com or gitlab.com. It needs the owner for a short guided run.

## Parts

| Part | What | Output |
|---|---|---|
| 1 | Seed script `scripts/acceptance/seed.mjs`: creates `~/Projects/shipyard-acceptance` with every artifact kind (specs and changes, decisions, questions, diagrams in each format, flows and bricks, costing sheets, plan, team, time, test plans, documents, learning paths, personas, slides). Idempotent. `--remote github` creates or reuses the private repository `me-cedric/shipyard-acceptance` and pushes; `--remote gitlab` does the same on gitlab.com. | a sample project that the app opens |
| 2 | Live backend tests, gated by `SHIPYARD_LIVE=1`, in `crates/shipyard-app/tests/live_*.rs`: open the seed project, forge calls (branches, pull request create, review, merge, close), tracker calls (GitHub Issues: create, label, assign, comment), sync, spec archive in a pull request, publish a local project. The token comes from the environment at run time (`GH_TOKEN=$(gh auth token)`), never from a file or an argument. | a pass list per feature against the real forge |
| 3 | Persona walkthroughs with Playwright on the browser build, with the demo data built from the seed project: one script per profile (project manager, architect, developer, tester, business analyst, functional lead, junior). Each script does the first hour of that profile, takes a screenshot per step and counts clicks. | screenshots and a step log per profile |
| 4 | Ease-of-use review (Opus, fresh context): reads the step logs and screenshots against the planned features and the rules in `.agents/progress/w11.md`. Ranked findings: dead ends, unclear words, wrong defaults, too many steps, a profile that lands on the wrong page. | a ranked finding list, then fixes |
| 5 | Guided run with the owner on the installed app: GitHub and GitLab browser sign-in, the GitLab MCP switch (item 39), the update check, opening the seed project. | a short pass list |

## Rules

- The test repository stays private and holds only sample data.
- No secret in the seed script, the tests, the logs or the screenshots.
- Live tests never run in CI unless the owner adds a secret for them.
- At most 4 agents at a time, 2 writers on files that do not overlap.
